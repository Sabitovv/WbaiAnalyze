# Контроль качества импорта Wildberries

Дата: 2026-08-01

## Цель

Не допускать, чтобы повреждённый, неполный или аномальный ответ Wildberries заменял ранее проверенные данные в рабочих отчётах. Каждый импорт должен сначала сформировать и проверить кандидат данных, а затем либо атомарно сохранить его, либо оставить прежние данные без изменений.

## Гарантии и ограничения

После внедрения система гарантирует, что:

- рабочие таблицы обновляются только кандидатом, прошедшим проверки;
- принятые `qty` и выручка соответствуют последнему принятому ответу финансового API WB;
- сумма детализации совпадает с агрегатами кабинета;
- расчётные показатели сходятся с формулами приложения;
- заблокированный импорт не удаляет и не перезаписывает прежние данные;
- результат каждой попытки сохраняется в журнале и доступен администратору;
- открытие приложения и отчётов не обращается к API WB.

Система не может гарантировать полное совпадение с интерфейсом кабинета WB в любой момент времени, потому что:

- интерфейс и API WB могут обновляться с разной задержкой;
- текущий и предыдущий календарные дни могут корректироваться WB;
- реклама поступает из отдельного API;
- себестоимость берётся из внутреннего справочника приложения;
- прибыль, логистика, возвраты и часть комиссий рассчитываются по настройкам приложения.

Статус `Проверено` означает совпадение с последним успешно полученным ответом API WB и прохождение внутренних проверок, а не неизменность данных со стороны WB в будущем.

## Область изменений

В объём входят:

- финансовый импорт `reportDetailByPeriod`;
- оперативный импорт `supplier/sales`;
- рекламный импорт;
- планировщик и ручной импорт;
- журнал попыток и статусы;
- отображение статусов в административном разделе;
- автоматические тесты валидатора и транзакционной записи.

В объём не входят:

- хранение полных сырых ответов WB;
- вызов WB API при открытии пользовательских отчётов;
- изменение бизнес-формул себестоимости или прибыли;
- внешние уведомления в Telegram, email или другие системы.

## Архитектура

### Поток импорта

1. Планировщик раз в 6 часов или администратор вручную запускает импорт.
2. Импортёр получает финансовые и рекламные данные WB с существующим ограничением параллельности.
3. Ответ нормализуется и фильтруется в памяти без изменения рабочих таблиц.
4. Из нормализованных строк строится кандидат агрегатов и детализации.
5. Чистый валидатор сравнивает ответ, кандидат и ранее принятые данные.
6. При временной или аномальной ошибке выполняются не более двух повторов.
7. Если кандидат прошёл проверки, он сохраняется одной транзакцией под advisory lock кабинета.
8. Если кандидат не прошёл проверки, транзакция записи не начинается, прежние данные сохраняются.
9. Каждая попытка завершается записью безопасных контрольных показателей в журнал.
10. Ошибка одного кабинета не останавливает импорт остальных кабинетов.

### Границы компонентов

`wb.js` отвечает за получение, нормализацию, построение кандидата и транзакционную запись.

Новый модуль `wbImportValidation.js` отвечает только за проверки. Он не обращается к сети и не изменяет БД. На вход он получает запрошенный период, нормализованные строки, рассчитанный кандидат, данные предыдущего импорта и метаданные каталога. На выходе возвращает:

```js
{
  ok: true,
  status: 'verified',
  issues: [],
  metrics: {}
}
```

или результат с `ok: false`, критическими причинами и контрольными метриками.

`scheduler.js` управляет расписанием, повторами на уровне кабинета и независимостью кабинетов.

`index.js` предоставляет чтение журнала и существующие ручные команды импорта.

## Статусы

Пользовательские статусы:

- `Предварительно`: импорт принят, но период включает сегодня или предыдущий календарный день;
- `Проверено`: импорт принят и все его даты старше предыдущего календарного дня;
- `Заблокировано`: кандидат не принят, прежние рабочие данные сохранены.

Внутренне журнал также может использовать `running` для незавершённой попытки и `failed` для сетевой или системной ошибки, при которой кандидат не был построен. В интерфейсе `failed` отображается как `Заблокировано` с причиной.

## Проверки

### Критические ошибки

Кандидат блокируется, если выполняется хотя бы одно условие:

- ответ финансового API не является массивом;
- финансовая строка не содержит корректной даты, типа документа, артикула, количества или денежного значения;
- числовое поле содержит `NaN`, `Infinity` или значение вне допустимого числового диапазона;
- после фильтрации не осталось корректных строк, но в БД уже есть ненулевые данные за этот период;
- один `rrd_id` повторяется в ответе и может привести к двойному учёту;
- сумма дневной детализации не совпадает с агрегатом по `qty`, выручке, себестоимости или комиссии с допуском 0,01;
- сумма менеджеров и непривязанных артикулов не совпадает с итогом кабинета с допуском 0,01;
- прибыль не совпадает с формулой приложения с допуском 0,01;
- автоматическая карточка аксессуара использовала себестоимость или габариты полного товара;
- по уже заполненному закрытому дню `qty`, выручка или себестоимость изменились более чем на 80%, если прежнее значение не является малым: минимум 5 единиц для `qty` и 50 000 тенге для денежных показателей;
- все полученные финансовые строки относятся к датам вне запрошенного периода.

Строки с датами вне запрошенного периода не импортируются. Если в запрошенном периоде остаются корректные строки, это считается предупреждением, а не блокировкой. Это учитывает фактическое поведение WB, когда ответ на однодневный запрос может включить соседнюю дату.

Если WB корректно вернул пустой период и ранее принятых данных за него нет, импорт фиксирует проверенный пустой результат без создания нулевых строк продаж.

### Предупреждения

Импорт может быть принят с предупреждением, если:

- служебные нефинансовые строки были исключены;
- ответ содержал строки вне запрошенного периода, но внутри периода остались корректные данные;
- появились неизвестные артикулы;
- изменились предмет, категория или отображаемое название товара;
- комиссия или реклама заметно изменилась, но критический порог не достигнут;
- часть свежего периода ещё доступна только через оперативный API.

Предупреждения сохраняются в журнале и не скрываются после успешной записи.

## Повторы и rate limit

- Обычный успешный импорт не выполняет дополнительных запросов ради проверки.
- При сетевой ошибке, `429`, повреждённом или аномальном ответе выполняются максимум два повтора.
- Для `429` учитывается `Retry-After`, если WB его передал; иначе применяется увеличивающаяся задержка.
- Кабинеты продолжают обрабатываться последовательно с текущей параллельностью `1`.
- Между диапазонами одного кабинета сохраняется пауза.
- Открытие админки, dashboard или любого отчёта читает только PostgreSQL и журнал импорта.

Таким образом, дополнительная проверка не увеличивает число WB-запросов при нормальной работе и расходует лимит только для восстановления после подозрительной попытки.

## Транзакционность и конкуренция

Кандидат строится до транзакции. После успешной проверки импортёр:

1. открывает транзакцию;
2. получает `pg_advisory_xact_lock(cab.id)`;
3. повторно читает контрольные метрики заменяемых дат, чтобы исключить гонку;
4. удаляет заменяемую детализацию;
5. выполняет upsert агрегатов и вставку детализации;
6. обновляет дневные статусы;
7. фиксирует транзакцию.

Любая ошибка приводит к `ROLLBACK`. Ручной импорт, scheduler и backfill используют один путь проверки и записи.

## Схема данных

### `wb_import_runs`

Журнал каждой попытки:

- `id BIGSERIAL PRIMARY KEY`;
- `cab_id INTEGER REFERENCES cabs(id) ON DELETE CASCADE`;
- `requested_from DATE NOT NULL`;
- `requested_to DATE NOT NULL`;
- `actual_from DATE`;
- `actual_to DATE`;
- `status TEXT NOT NULL`;
- `attempts INTEGER NOT NULL DEFAULT 1`;
- `fetched_rows INTEGER NOT NULL DEFAULT 0`;
- `accepted_rows INTEGER NOT NULL DEFAULT 0`;
- `rejected_rows INTEGER NOT NULL DEFAULT 0`;
- `source_metrics JSONB NOT NULL DEFAULT '{}'`;
- `candidate_metrics JSONB NOT NULL DEFAULT '{}'`;
- `issues JSONB NOT NULL DEFAULT '[]'`;
- `started_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`;
- `finished_at TIMESTAMPTZ`.

Полный payload, токен, HTTP-заголовки и персональные данные WB в журнал не записываются.

### `wb_import_days`

Текущий статус данных по кабинету и дате:

- `cab_id INTEGER REFERENCES cabs(id) ON DELETE CASCADE`;
- `date DATE NOT NULL`;
- `accepted_run_id BIGINT REFERENCES wb_import_runs(id)`;
- `accepted_status TEXT`;
- `accepted_at TIMESTAMPTZ`;
- `last_attempt_run_id BIGINT REFERENCES wb_import_runs(id)`;
- `last_attempt_status TEXT NOT NULL`;
- `checked_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`;
- `issues JSONB NOT NULL DEFAULT '[]'`;
- `PRIMARY KEY (cab_id, date)`.

При блокировке обновляются только поля последней попытки. Ссылка на последний принятый импорт и его статус сохраняется.

Обе таблицы создаются в `migrate.js` и в startup compatibility migrations `index.js`.

## API и административный интерфейс

`GET /api/wb/import-runs` возвращает последние попытки с фильтрами `cabId`, `dateFrom`, `dateTo` и ограниченным количеством записей.

`GET /api/wb/import-status` возвращает краткий статус по кабинетам и датам без сырых payload.

Существующие ручные endpoints импорта возвращают дополнительно:

- `runId`;
- `status`;
- `attempts`;
- `fetchedRows`;
- `acceptedRows`;
- `rejectedRows`;
- `issues`;
- признак `previousDataPreserved`.

В разделе кабинетов админки отображаются:

- общий статус фонового импорта;
- статус последней попытки каждого кабинета;
- запрошенный и фактически принятый период;
- количество полученных, принятых и отклонённых строк;
- предупреждения и причины блокировки;
- явное сообщение, что при блокировке сохранены прежние данные.

Интерфейс опрашивает только backend status endpoints и не вызывает WB API.

## Обработка ошибок

- Сетевая ошибка: повторить до двух раз, затем записать `failed`, рабочие данные не менять.
- `429`: ожидать разрешённое время и повторить в пределах лимита попыток.
- Ошибка валидации: повторно получить данные; после двух повторов записать `blocked`.
- Ошибка БД во время записи: откатить транзакцию и записать `failed` отдельным безопасным запросом.
- Ошибка одного кабинета: продолжить остальные кабинеты и показать ошибку в общем результате scheduler.
- Перезапуск backend: незавершённые старые записи `running` считаются `failed` при следующем запуске или чтении статуса.

## Тестирование

### Модульные тесты валидатора

- корректный финансовый ответ;
- корректный пустой период;
- повреждённый формат ответа;
- финансовая строка без обязательного поля;
- служебные строки;
- строки вне периода;
- ответ только с датами вне периода;
- повторяющийся `rrd_id`;
- неизвестный артикул;
- аксессуар с автоматической карточкой полного товара;
- вручную настроенный аксессуар;
- `NaN` и бесконечные значения;
- несовпадение агрегатов и детализации;
- неправильная формула прибыли;
- изменение закрытого дня выше и ниже порога 80%;
- малые значения, для которых порог блокировки не применяется.

### Интеграционные тесты

- успешный кандидат атомарно заменяет выбранные даты;
- заблокированный кандидат не меняет `wb_sales`, `wb_manager_sales` и `wb_manager_sales_detail`;
- ошибка в середине записи вызывает полный rollback;
- advisory lock не позволяет двум импортам одного кабинета пересечься;
- два временных сбоя завершаются успешной третьей попыткой;
- три подозрительных ответа завершаются блокировкой;
- ошибка одного кабинета не прерывает остальные;
- журнал не содержит токены или полный payload;
- суммы daily, monthly, category, article, product и dashboard совпадают после принятого импорта.

### Проверка интерфейса

- админка показывает каждый пользовательский статус;
- причина блокировки читаема и содержит кабинет и период;
- при блокировке отображается, что прежние данные сохранены;
- многократное открытие страниц не создаёт WB API-запросы;
- frontend проходит lint и production build.

## Развёртывание

1. Очистить существующие ошибочные автоматические карточки аксессуаров или привести их стоимость и габариты к корректным значениям.
2. Применить миграции таблиц журнала.
3. Развернуть валидатор и новый транзакционный поток.
4. Запустить один ручной импорт небольшого закрытого периода для каждого кабинета.
5. Проверить журнал и согласованность всех отчётов.
6. Включить scheduler с прежним интервалом 6 часов.
7. Наблюдать первые сутки за блокировками и предупреждениями, не ослабляя критические инварианты.

## Критерии приёмки

- повреждённый кандидат не меняет ни одну рабочую таблицу продаж;
- прежние проверенные данные остаются доступны после блокировки;
- при обычном успешном импорте не выполняются дополнительные WB-запросы;
- число повторов ограничено двумя;
- открытие UI не вызывает WB API;
- журнал переживает перезапуск backend;
- администратор видит статус и конкретные причины по каждому кабинету;
- после успешного импорта все отчётные разрезы и dashboard сходятся по общим метрикам;
- тесты, синтаксическая проверка, frontend lint и frontend build проходят.
